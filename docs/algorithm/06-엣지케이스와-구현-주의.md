# 6. 구현상의 함정과 수치적 안정성

본 장은 §2 부터 §4 까지의 정상 경로 기술과 별개로, 본 시스템의 실제 구현 과정에서 드러난 엣지 케이스와 수치적 안정성 보장 처리, 그리고 위협 모델의 한계를 정리한다. 각 절은 (i) 함정이 발생하는 조건, (ii) 본 코드가 이를 어떻게 차단하는가 (또는 차단하지 않는가), (iii) 차단되지 않은 경우의 후속 작업의 세 가지 관점에서 기술된다. 부록 §6.A 는 §2.A 의 N = 4 예제 위에서 β₂ = 0 가 transparent ciphertext 예외를 유발하는 시나리오를 손 계산으로 추적한다.

## 6.1 데이터 가정의 부수 효과

### 6.1.1 가중치 필터링과 불신 신호의 소실

§1.4 에서 명시한 바와 같이 본 시스템의 csv 파서는 `parts[2] >= 2` 의 조건만 수용한다. BitcoinOTC 의 가중치 분포가 −10 부터 +10 사이의 정수임을 고려하면, 이 필터는 음수, 0, 그리고 +1 평점을 모두 거부한다. 원본 35,592 행 중 23,611 행이 입력 단계에서 사라진다.

이 가정이 의미 모델에 미치는 영향은 다음의 세 가지이다.

첫째, 불신 신호의 완전한 소실이다. PageRank 가 인식하는 그래프는 "신뢰만이 흐르는 그래프" 가 된다. 어떤 노드가 다른 노드에게 −10 의 평점을 부여하였더라도 그 정보는 사라지므로, 본 시스템은 "이 노드가 신뢰를 받지 못한다" 는 사실은 알 수 있으나 "다른 노드들이 이 노드를 명시적으로 의심한다" 는 사실은 알 수 없다.

둘째, 자연 sybil 의 빈도 차감 효과이다. 자연 sybil 후보 노드의 식별이 음수 평점에 의존함에도 그 신호가 필터링 후 사라지므로, 후속 검증에서의 sybil 후보군은 원본 csv 의 음수 평점 기록을 *외부* 에서 추출하여 별도로 구성된다.

셋째, 합성 sybil 데이터셋의 가중치 선택에 대한 제약이다. 합성 dataset 의 sybil-to-sybil 평점을 5, 외부 평점을 2 로 둔 설계 선택은 본 필터의 가정에 의해 강제된다. 외부 평점이 1 이하인 경우 sybil 노드의 빈도가 컷오프 이하로 떨어져 top-N 에 포함되지 못한다.

본 필터를 완화하면 정보량은 증가하나 의미 모델 자체가 바뀐다. "낮은 신뢰" 와 "불신" 을 동일한 척도에 둘 것인가의 설계 결정에 해당하며, 본 보고서의 범위를 벗어난다.

### 6.1.2 시간 감쇠와 자연 가지치기

§2.2 에서 도입한 반감기 1 년의 지수 감쇠는 오래된 거래를 자동으로 약화시킨다. 9 년 전의 weight = 2 거래는 2 · 0.5⁹ ≈ 0.004 로 감쇠하여 가지치기 임계값 θ = 0.05 보다 한 자리수 작은 값을 가진다. 따라서 이러한 간선은 인접 리스트에는 등록되나 2-홉 전파에서 항상 제외된다.

데이터셋의 maxTime ≈ 2016 년 1 월이고 csv 의 첫 시점이 2010 년 11 월임을 고려하면, 평균적인 거래는 데이터셋 시점 기준 5 년이며 그 감쇠 계수는 0.5⁵ = 0.03125 이다. weight ≥ 32 의 raw 평점이 있어야 시간 감쇠 후에도 1.0 을 상회한다. BitcoinOTC 의 raw 평점이 ±10 한계를 가지므로, 5 년 이상의 거래는 사실상 모두 2-홉 전파에서 제외된다.

요약하면 §2.4 의 가지치기는 2-홉 전파의 시간 윈도를 약 4–5 년 안쪽으로 좁히는 자연스러운 부수 효과를 갖는다. θ = 0 으로 설정하는 검증 모드에서는 이 윈도가 사라지고 모든 오래된 거래가 약하게나마 2-홉 으로 흐르게 된다.

### 6.1.3 중복 간선의 누적

`outAdj[srcIdx].push_back(...)` 와 `outM_pub[tgtIdx][srcIdx] += w` 의 결합은 동일한 (src, tgt) 쌍이 csv 의 여러 행에 나타나는 경우 그 가중치를 누적한다. BitcoinOTC 에서 동일한 두 지갑이 여러 번 거래한 사례는 자연스럽게 가중치의 합산으로 표현된다.

원본 데이터셋에서 한 (src, tgt) 쌍은 평균 1.1 회 등장한다. 대부분의 쌍은 한 번 등장하나 일부 쌍은 여러 번이며, 일부 쌍에 *대립되는 평점* 이 섞여 있는 경우 (예: 한 번은 +4, 다른 번은 −8) 음수 거래는 §6.1.1 의 필터에 의해 제거되므로 양수만 누적되어 왜곡된 합계가 산출된다. 본 보고서는 이 점을 §6.1.1 가정의 가시적 부수 효과로 분류하고 추가 처리를 도입하지 않는다.

## 6.2 청크 경계와 회전 안전

§3.5 의 보조정리 3.1 과 3.2 가 정의하는 청크 경계 안전성은 Q7 패딩의 존재에 의존한다. 통합 단계 (`feat/bgsg-sparse-integrated` 브랜치) 의 §2.6 코드

```cpp
int slot_idx = (row + j * m1) % nGlobal;
diag[c * pirBlockSize + slot_idx] = val;
diag[c * pirBlockSize + slot_idx + nGlobal] = val;   // Q7
```

는 두 줄 모두가 보조정리 3.1 의 가정 (청크 안 두 영역의 평문 동일성) 을 만족시킨다. 두 줄 중 하나라도 누락되면 다중 청크 환경에서의 등가성 R6 검증이 즉시 실패한다.

`slot_count` 가 `pirBlockSize = 2N` 의 정수배가 아닌 경우 마지막 청크 뒤에 *틈* 이 발생한다. 이 영역은 0 으로 채워지나, CKKS 회전이 slot_count 단위 cyclic 이므로 첫 청크의 앞 슬롯과 마지막 청크의 뒤 슬롯이 wrap-around 관계에 놓인다. `num_chunks · pirBlockSize ≤ slot_count` 가 보장되나 일반적으로 등호는 성립하지 않으므로 이 틈 영역이 존재한다.

다행히 첫 청크의 앞 슬롯이 회전을 통해 도달하는 위치가 마지막 청크의 *뒤쪽 0 영역* 인 한 결과에 영향을 주지 않는다 (0 과의 합은 무해). 다만 이 "마지막 청크 너머는 0" 조건이 깨지는 시나리오 — 예를 들어 빈 슬롯을 측정 정보로 활용하는 등의 변경 — 가 도입되면 즉시 안전성이 깨진다. 본 보고서의 현 구현에서는 이러한 변경이 도입되어 있지 않다.

## 6.3 Galois key step 집합의 의존성

CKKS 의 회전은 각 step 마다 별도의 Galois key 를 요구한다. SEAL 의 기본 키 생성 (`create_galois_keys()`) 은 2^k step 만 생성하며, 임의 step 의 회전은 이들의 합성으로 처리된다. 합성은 가능하나 *각각의 합성 단계마다 key-switching 1 회씩이 추가* 되므로, BSGS 의 baby/giant step 처럼 특정 step 집합이 반복적으로 사용되는 시나리오에서는 그 step 들을 키 생성 단계에서 직접 등록하는 것이 효율적이다.

본 시스템은 BSGS 결정 직후 step 집합을 구성하여 Galois key 를 직접 생성한다 (`CipherRank.cpp:213–229`).

```cpp
BSGSParams pirParams = FindOptimalAsymmetricBSGS(nGlobal, 1.0);
BSGSParams prParams  = FindOptimalAsymmetricBSGS(nSub,    1.0);
vector<int> stepsPir = ComputeBSGSStepSet(pirParams, nGlobal);
vector<int> stepsPr  = ComputeBSGSStepSet(prParams,  nSub);
set<int> unionSet(stepsPir.begin(), stepsPir.end());
unionSet.insert(stepsPr.begin(), stepsPr.end());
unionSet.insert(1);  unionSet.insert(16);    // 측정 dummy 회전용
galois_step_set_.assign(unionSet.begin(), unionSet.end());
```

본 구성에서 두 가지 함정을 명시한다.

첫째, step 1 과 step 16 의 명시적 삽입이다. Phase 5 의 weight 측정 dummy 회전 (`CipherRank.cpp:704, 710`) 이 이 두 step 을 사용하므로, 이들을 step 집합에 포함시키지 않으면 SEAL 가 예외를 던진다. 이 의존성은 코드 안에서 자동으로 검출되지 않으므로 (테스트 회전이 실행되어야 비로소 드러남) 주석으로 명시되어야 한다.

둘째, `giant_weight = 1.0` 가정의 함의이다. 측정된 baby/giant 비율이 1.0 이 아닌 경우 (예를 들어 2.0) `FindOptimalAsymmetricBSGS` 가 비대칭 (m₁, m₂) 를 반환해야 하며, 그 결과 Galois key step 집합도 다시 계산되어야 한다. 이 *두 번째 키 생성 단계* (통합 명세의 B0 Three-Pass) 는 현재 구현되어 있지 않다. 측정된 weight 가 [1.0, 5.0] 의 범위로 클램핑되어 있으나 (`CipherRank.cpp:716–717`), 그 값이 (m₁, m₂) 의 결정에 영향을 주지 않으므로 사실상 측정 후 사용되지 않는 정보로 남는다.

후속 작업으로 분리한 항목이며, 본 측정 환경에서의 baby/giant 비율이 1.0 에 근접함에 따라 실용적 회귀는 관측되지 않는다.

## 6.4 Transparent ciphertext 와 가드 추가

β₂ = 0 으로 설정한 sweep 의 한 행 전체가 SEAL 의 `result ciphertext is transparent` 예외로 실패한 사례가 있다. 본 절은 그 메커니즘을 형식적으로 기술하고 수정의 정당성을 논의한다.

β₂ = 0 의 경우 §2.4 의 2-홉 누적의 모든 contribution 이 0 이 된다. 그러나 누적 자체는 시도되므로 `localDiag[d2][dst] += 0` 의 라인이 매 (src, mid, dst) 트리플마다 실행되며, `unordered_map<int, double>` 의 `operator[]` 가 미존재 키에 대해 0 값을 자동 *삽입* 하는 특성으로 인해 `(dst, 0.0)` entry 가 정식 항목으로 등록된다.

이 entry 들이 reduce 단계까지 살아남는다. `merged[d][row] += 0.0` 의 결과 std::map 에 `(row, 0.0)` 가 정식 entry 로 남으며, 가드가 없는 경우 sorted vector 로 옮길 때 *값이 모두 0 인 비공실 sparseDiag[d]* 가 산출된다.

BSGS 의 인코딩 루프 `if (sparseDiag[d].empty()) continue;` 가드는 *비공실* 한 d 를 모두 통과시킨다. 따라서 위 비공실-전영 (entirely-zero non-empty) sparseDiag[d] 가 BsgsDiag 인코딩 단계에 진입하여, 모든 슬롯이 0 인 vector 가 CKKS encode 되어 *모든 계수가 0 인 Plaintext* 를 생성한다. Phase 3 의

```cpp
thread_evaluator.multiply_plain_inplace(multiplied, item.plain);
```

가 이 평문과의 곱을 수행하면 결과 ciphertext 의 모든 슬롯이 0 으로 떨어진다. SEAL 의 정의상 이러한 ciphertext 는 transparent — 비밀키 없이도 평문이 모두 0 임이 자명 — 이며, 보안 위험으로 분류되어 `std::logic_error` 가 던져진다.

수정은 reduce 후 sorted vector 변환 시점에 `val != 0.0` 가드를 추가하는 단일 행으로 충분하다 (`CipherRank.cpp:464–468`).

```cpp
for (int d = 0; d < nGlobal; d++) {
    for (const auto& [row, val] : merged[d])
        if (val != 0.0) sparseDiag[d].emplace_back(row, val);
}
```

본 가드 적용 후 β₂ = 0 의 d 에 대해서는 entry 가 모두 제거되어 비공실 조건이 만족되지 않으므로 BsgsDiag 인코딩이 자연스럽게 스킵된다. 손 계산 트레이스는 §6.A 에 별도로 수록한다.

본 사례의 학술적 의의는 *알고리즘 수준의 의미 모델 변경* 이 *암호학 라이브러리의 zero-padding 가정* 을 노출시키는 패턴을 보였다는 점이다. 유사한 패턴의 후속 버그가 hub-aware Phase 1 (Q3) 이나 main-style fallback (B8) 의 도입 단계에서도 발생할 수 있으며, 사전 손 트레이스를 통한 검증의 필요성을 시사한다.

## 6.5 CKKS scale 관리

BSGS 의 누적은 `multiply_plain` → `rescale_to_next_inplace` → `add_inplace` 의 순서로 수행된다. CKKS 의 `multiply_plain` 은 두 인자의 scale 을 곱하고, rescale 은 그 곱한 scale 을 한 단계 prime 으로 나누어 원래 scale 의 근사값으로 복원한다. 그러나 prime 의 실제 값이 정확히 scale 의 정수배가 아니므로, rescale 결과의 scale 은 원래 값으로부터 미세하게 어긋난다.

이 미세 차이가 누적되면 ciphertext 들 사이의 scale 이 점진적으로 흩어지고, `add_inplace` 가 scale mismatch 로 예외를 던진다. 본 시스템은 매 rescale 후

```cpp
multiplied.scale() = scale;
```

로 scale 을 강제 동일화한다. 수학적으로 본 처리는 ciphertext 안의 값이 약간의 비율 차이로 어긋난 상태에서 더해지는 것을 허용한다는 의미이나, 실측 결과 그 차이는 노이즈 floor 안에 묻힌다. §4.4 에서 도입한 평문 멱법과의 비교에서 Precision Error 가 무시 가능한 수준으로 측정되는 점이 그 증거이다.

`mod_switch_to_inplace` 의 호출도 동일한 맥락에 속한다. 누적 결과의 modulus chain 레벨을 새 ciphertext 의 레벨에 *맞추어* 더할 수 있게 한다. modulus chain 이 동일하지 않은 경우 SEAL 가 add 를 거부한다.

## 6.6 Cross-run 결정성과 unordered_map

libstdc++ 와 libc++ 의 `unordered_map` 은 해시 함수의 시드가 프로세스 내에서는 결정적이나 프로세스 간 동일성을 보장하지 않는다. 따라서 동일한 입력에 대해 서로 다른 시점의 binary 실행에서 이터레이션 순서가 달라질 가능성이 있다.

이 비결정성이 영향을 미치는 자리는 다음 두 곳이다.

첫째, `frequency` 의 빈도 동률 노드들 사이의 인덱스 부여 순서이다. 두 노드의 빈도가 동일한 경우 어느 쪽이 더 작은 globalIdx 를 부여받을지가 unordered_map 의 이터레이션 순서에 의존한다. BitcoinOTC 의 상위 1024 위 노드는 대부분 빈도가 서로 다르므로 실측에서는 영향이 관측되지 않으나, 더 변동성이 큰 데이터셋의 경우 `std::map` 으로의 교체를 통해 결정성을 강화하는 것이 안전하다.

둘째, `sparseDiag` 자체의 누적 순서이다. 그러나 §2.5 에서 도입한 std::map 기반의 reduce 단계가 row 오름차순으로의 직렬화를 강제하므로, 직렬화 후의 순서는 결정적이다. 즉 cross-run 비결정성이 점수에 영향을 주지 않도록 *직렬화 시점* 의 결정성, *부동소수점 누적 순서* 의 결정성 (thread_id 순서), *읽기 순회* 의 결정성 (단일 encode 호출) 의 세 층이 모두 보장된다.

## 6.7 단일 당사자 모델의 한계와 후속 확장

§1.5 와 §4.5 에서 명시한 바와 같이, 본 시스템의 Phase 5 는 매 반복마다 복호 후 재암호화를 수행하므로 서버가 비밀키를 소유한다. 이는 PIR 의 엄격한 위협 모델에 부합하지 않으며, 본 시스템에서 의미가 있는 보안 보장은 다음의 세 가지로 한정된다.

(i) Phase 3 의 출력은 평가 대상 인덱스의 명시적 함수가 아니다. one-hot 의 1 위치는 ciphertext 내부에서만 의미가 정의된다.

(ii) wall-clock 측정값은 평가 대상과 무관하다. BSGS 가 동일한 수의 회전을 동일한 step 집합으로 수행하므로 평가 대상의 식별 시도에 timing 부채널이 형성되지 않는다.

(iii) 연산에 사용되는 데이터 (BsgsDiag, M_pub) 는 평가 대상과 무관하다. Phase 1 의 출력은 평가 대상이 결정되기 전에 생성되므로, 평가 대상에 따른 데이터 의존성이 존재하지 않는다.

진정한 PIR 위협 모델로의 확장은 다음 세 가지 방향이 가능하다.

(a) Phase 5 의 복호-재암호 루프를 동형 정규화로 대체. 이 경우 매 반복의 sum-to-1 정규화와 음수 절단을 동형으로 표현해야 하며, 절단의 비선형성으로 인해 다항식 근사가 요구된다.

(b) 반복 횟수를 useful depth 안으로 축소. ITER = 1–2 로 제한하면 modulus 사슬 내에서 동형 곱이 가능하나, 수렴이 보장되지 않는다.

(c) Bootstrapping 도입. CKKS bootstrapping 의 추가는 모든 useful depth 한계를 해소하나, SEAL 4.1.2 가 이를 지원하지 않으므로 라이브러리 전환이 필요하다.

세 방향 모두 본 보고서의 범위를 벗어나며, 별도의 설계 명세에서 다룬다.

## 6.8 측정 환경의 함정

### 6.8.1 열 부하 (thermal load)

장시간 sweep 의 실행 결과 wall-clock 이 25–40 % 증가하는 현상이 반복적으로 관측되었다. 측정 사이에 60 초의 idle 을 둘 경우 회복된다. 단일 cold 측정이 가장 정확한 수치를 제공하나 통계적 신뢰도가 낮고, 다회 warm 측정이 통계적 신뢰도는 높으나 시스템 부하가 측정에 혼입된다.

본 보고서가 인용하는 측정값은 다음의 원칙을 따른다.

- 단일 측정 (MVB) 은 cold 머신 기준으로 산출.
- N = 3 의 sweep 은 측정 사이의 짧은 휴식만을 가지므로 warm 머신 영향이 일부 혼입.
- N = 10 의 batch 는 sustained-load 환경으로, 8.5 초 수준의 outlier 가 thermal artifact 임을 명시.
- 합성 sweep 의 일부 cell (β₂ = 1.0, θ ≤ 0.05) 에서 한 run 의 wall-clock 이 1056 초까지 도달한 사례가 있으며, 동일 cell 의 cold 측정값이 3.7 초임을 고려할 때 75 배의 변동이 시스템 부하만으로 설명되는 사례에 해당.

이 변동을 학술적으로 깔끔하게 정리하기 위해서는 별도의 측정 환경 (전용 머신 또는 reserved 인스턴스) 이 요구된다. 본 보고서는 단일 머신의 한계 내에서 honest reporting 을 원칙으로 한다.

### 6.8.2 OpenMP 스레드 수의 상한

OpenMP P = 4 가 본 측정 환경에서의 실용적 최적이다. P = 8 까지는 5 청크 (Config B) 가 두 batch 로 처리되어 가속 효과가 의미를 가지나, P = 16 의 경우 oversubscription 으로 인한 thread 간 cache contention 으로 오히려 감속이 관측된다. 본 한계는 머신의 코어 수 (4) 와 청크 수 (5) 의 곱셈적 한계에 기인하며, 코드 변경으로는 해소되지 않는다. 청크 수가 더 큰 시나리오 (예: num_targets = 256) 에서만 P > 4 가 의미를 가진다.

### 6.8.3 판정 일치가 알고리즘 등가를 함의하지 않음

Phase 6 의 `APPROVED` / `REJECTED` 출력은 임계값 0.0150 의 위·아래만을 본다. 그 위·아래의 *실제 점수* 가 다르면 알고리즘이 다르다. baseline 과 통합 B 가 동일한 판정을 산출하는 경우라도 점수는 일반적으로 다르며 (§1.6 의 Wallet 1, 35 사례), 이러한 점수 차이를 검출하기 위해 R1, R2, R6 검증은 *점수의 ε-등가성* 까지 확인한다.

## 6.9 후속 작업

본 보고서의 범위를 벗어나며 별도 명세로 분리한 후속 항목을 알고리즘 관점에서 정리한다.

- **B0 Three-Pass.** weight 자동 측정 → BSGS 파라미터 결정 → Galois key 재생성의 사이클. 현재는 weight = 1.0 의 고정값으로 우회되어 있다 (§6.3).
- **B2 phase-kind cost function.** Phase 3 과 Phase 5 의 BSGS 비용이 서로 다른 차원의 행렬에 대해 정의되므로 별도의 최적화 함수가 적용되어야 한다. 현재는 동일 함수에 N 과 n 을 인자로 전달하는 약식이 사용된다.
- **B8 main-style fallback.** D_sparse 가 작은 경우 BSGS 가 baseline 대비 *느릴* 수 있으며, 이러한 상황에서는 baseline 의 직접 회전 경로로 분기하는 fallback 이 필요하다. 현재는 advisory log 만 출력된다.
- **Q3 hub-aware Phase 1.** hub 노드의 2-홉 누적이 평균을 압도하는 경우 별도 처리를 통해 sweep 시간을 추가 단축할 수 있으나, sybil 시나리오의 변경 가능성으로 인해 별도의 보안 분석이 요구된다.
- **Hub-trust-mixed 합성 sybil.** 현재의 합성 sybil 은 완전히 격리된 mutual ring 의 형태이다. sybil 이 실제 trust hub 와도 약하게 연결된 위장 sybil 모델에서는 B-default 와 B-C2 의 차이가 의미를 가질 가능성이 있으며, 후속 사용자 케이스 검증이 요구된다.
- **다중 데이터셋 일반화.** BitcoinOTC 의 가중치 척도와 시간 분포 가정이 다른 데이터셋으로 이전할 때 어떻게 무너지는가에 대한 분석이 요구된다. β 와 θ 의 의미는 데이터셋마다 재 calibration 되어야 한다.

위 항목들은 각각 별도의 NG (No-Go) 절 또는 O (Open question) 절로 통합 명세에 cross-reference 되어 있다.

## 부록 6.A — β₂ = 0 의 transparent ciphertext 손 추적

§6.4 의 메커니즘을 §1.6 의 N = 4 예제 위에서 손 계산으로 추적한다. 본 부록의 목적은 어떤 d 가 transparent 평문을 산출하는지 구체적인 수치로 보이는 데 있다.

### 6.A.1 β₂ = 0 하에서의 sparseDiag

동일한 6 행의 csv 에 β₂ = 0 을 적용하면 §2.A.2 의 누적 식에서 모든 2-홉 항이 0 으로 떨어진다. 1-홉 항만으로 sparseDiag 를 재계산하면 다음과 같다.

| d | 1-홉 누적 결과 (β₂ = 0) |
|---:|---|
| 0 | 비공실 항 없음 (self-loop 부재) |
| 1 | { 0 : 4, 1 : 5 } |
| 2 | { 2 : 4, 3 : 2 } |
| 3 | { 0 : 3, 1 : 3 } |

해석. d = 1 은 (src − mid) mod 4 = 1 인 1-홉 간선만을 수집한다. src = 1, mid = 0 의 30 → 10 (w = 4) 가 (d = 1, row = 0) 에 4 를 부여하며, src = 2, mid = 1 의 20 → 30 (w = 5) 가 (d = 1, row = 1) 에 5 를 부여한다. d = 0 은 self-loop 가 존재해야 채워지는 자리이나, BitcoinOTC 에는 self-loop 가 없으므로 비공실 항이 형성되지 않는다.

§2.A.3 의 M_pub 의 d 번째 대각선과 비교한다.

- d = 0: (0, 0, 0, 0) — 모두 0, 비공실 항 부재 ✓
- d = 1: (M[0][1], M[1][2], M[2][3], M[3][0]) = (4, 5, 0, 0). 비영 항만 추출하면 {0:4, 1:5} ✓
- d = 2: (0, 0, 4, 2) → {2:4, 3:2} ✓
- d = 3: (3, 3, 0, 0) → {0:3, 1:3} ✓

모든 d 에서 일치가 확인된다.

### 6.A.2 가드 부재 시의 동작

§6.4 의 메커니즘을 본 예제에 대입하여 추적한다. β₂ = 0 의 누적 루프가 시도하는 2-홉 항 중 일부의 (src, mid, dst) 트리플을 살펴본다.

src = 0, mid = 1, dst = 0 의 트리플 (10 → 30 → 10) 에서 d₂ = 0, 누적값 = β₂ · 3 · 4 = 0. `localDiag[0][0] += 0` 가 실행되면서 (d = 0, row = 0, val = 0.0) 의 entry 가 등록된다. d = 0 은 1-홉 으로는 비공실 항이 형성되지 않는 자리이므로, 가드가 없는 경우 sparseDiag[0] = [(0, 0.0)] 의 *비공실-전영* 상태로 남는다.

마찬가지로 src = 1, mid = 0, dst = 2 의 트리플은 (d = 3, row = 2, val = 0) 의 entry 를, src = 2, mid = 1, dst = 0 의 트리플은 (d = 2, row = 0, val = 0) 의 entry 를 만들어낸다. d = 1 의 자리에서는 1-홉 contribution 이 비영이므로 0 entry 가 합산되어도 결과적으로는 비영 항이 유지된다.

§6.4 의 사유에 따라 d = 0 의 sparseDiag 가 비공실-전영 상태로 BsgsDiag 인코딩 단계에 진입하면, slot_count = 8 의 평문 벡터가 모두 0 인 Plaintext 가 생성된다. Phase 3 의 첫 번째 평문 곱 — 본 예제에서는 (i = 0, j = 0) 의 baby_steps[0] × plain_d0 의 `multiply_plain_inplace` 호출 — 가 즉시 transparent ciphertext 예외를 던진다.

### 6.A.3 가드 적용 후의 동작

§6.4 의 수정

```cpp
if (val != 0.0) sparseDiag[d].emplace_back(row, val);
```

이 적용된 코드는 본 예제의 (d = 0, 0, 0.0), (d = 3, 2, 0.0), (d = 2, 0, 0.0) entry 들을 모두 제거한다. d = 0 은 그 결과 비공실 항이 부재한 상태가 되어 `sparseDiag[0].empty()` 가드에 걸리며 BsgsDiag 인코딩이 스킵된다. D_sparse = 3 으로 정리되며, d = 1, 2, 3 의 BsgsDiag 만이 pirDiagonals 에 등록된다.

Phase 3 의 BSGS 곱셈은 § 3.A 의 흐름과 동일하게 진행되나, d = 0 항이 부재하므로 j = 0 의 누적이 (i = 1, d = 1) 항만으로 구성된다. 결과 ciphertext 의 슬롯에는 1-홉 의미 모델 하의 trust 분포 `[M_pub[0][1], M_pub[1][1], M_pub[2][1], M_pub[3][1]] = [4, 0, 0, 2]` 가 인코딩된다.

본 결과는 β₂ = 0 의 의미 — 2-홉 전파가 완전히 차단되어 1-홉 신뢰만이 평가에 반영됨 — 와 정합한다. transparent ciphertext 예외 없이 Phase 3 끝까지의 통과가 보장되며, sweep 의 β₂ = 0 행 전체가 정상적으로 수렴한다.

### 6.A.4 학술적 의의

본 사례의 본질은 다음의 관찰에 있다. β · θ 의 의미 모델 변경이라는 *알고리즘 수준* 의 변경이, SEAL 의 보안 가정 (zero-padding 의 비허용) 이라는 *암호학 라이브러리 수준* 의 가정을 노출시킨다. 두 층의 사이에 놓인 가드 한 줄의 부재가 9 cell sweep 의 한 행 전체를 실패로 만든다는 점은, 본 시스템과 같이 *수치 알고리즘과 동형암호 라이브러리가 직접 결합* 된 구조의 후속 변경에서 사전 손 트레이스의 필요성을 재확인시킨다.

Q3 의 hub-aware Phase 1 이나 B8 의 main-style fallback 의 도입 단계에서도 유사한 패턴이 발생할 가능성이 존재한다. 본 부록과 같은 N = 4 의 작은 예제로 변경된 알고리즘이 *어떤 0 평문* 을 생성할 수 있는지를 사전에 추적하는 것이 안전한 접근이다.
