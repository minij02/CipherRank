# 1. 개요

CipherRank는 SNAP의 *Bitcoin OTC* 신뢰 그래프를 입력으로 받아, 임의의 지갑 하나의 trust score를 PageRank 기반으로 매기는 시스템이다. 평범한 PageRank 구현과의 결정적 차이는 두 가지다. 첫째, 그래프 위에 시간 감쇠와 신뢰 모델에 따른 가중치 변환이 들어간다. 둘째, 평가 대상이 누구인지는 서버에 노출하지 않는다 — 클라이언트가 one-hot 형태로 암호화한 인덱스를 던지면, 서버가 그 인덱스에 해당하는 부분 그래프를 동형으로 끌어내 동형 PageRank 까지 마무리한다.

이 문서는 그 흐름의 큰 그림을 보이고, 이후의 문서들에서 한 단계씩 풀어쓸 표기와 데이터 가정을 정리한다.

## 1.1 입력 데이터 — Bitcoin OTC

원본은 `soc-sign-bitcoinotc.csv`이고 한 줄당 `src,tgt,weight,time` 네 개의 필드를 가진다. weight 는 정수, time 은 유닉스 시각이다. 예를 들어,

```
6,2,4,1289241911.72836
```

는 "지갑 6 이 지갑 2 에게 시점 1289241911 (2010-11-08) 에 +4 의 신뢰 평점을 주었다"는 뜻이다. weight 는 -10 에서 +10 사이의 정수로, 양수는 신뢰, 음수는 불신을 의미한다.

원본 파일은 35,592 행이지만 코드 (sparse 알고리즘 기준 `CipherRank.cpp:228` 의 `parts[2] >= 2` 필터) 는 weight 가 2 미만인 간선은 모두 버린다. 이 필터를 통과하는 간선이 11,981 개, 등장 노드가 3,302 개다. d̄ = E / V = 3.628 이므로 평균 출차수가 4 미만인, 전형적인 sparse 사회 그래프다.

음수 평점이 데이터셋에 분명히 존재하지만 처음부터 제거되는 점은 알고리즘 전체에 비-사소한 영향을 준다 — 자세한 논의는 5절 ("엣지케이스") 로 미룬다.

## 1.2 표기와 파라미터

이후 문서들에서 반복적으로 쓸 기호를 한 곳에 모아둔다.

| 기호 | 의미 | 코드 / 기본값 |
|---|---|---|
| N | nGlobal — 빈도 상위 N 개 지갑으로 구성된 전역 인덱스 공간 | `-g`, 기본 256 |
| n | nSub — Phase 4 가 선택하는 부분 그래프의 차원 | `-s`, 기본 64 |
| K | num_chunks — 평가 대상을 SIMD 청크에 나눠 담은 결과의 청크 수 | `CipherRank.cpp:320` 계산 |
| P | OpenMP 스레드 수 | `omp_set_num_threads(4)` |
| β₁, β₂ | 1-hop / 2-hop 가중치 | 기본 1.0 / 0.30 |
| θ | 2-hop 전파를 차단할 1-hop 임계값 | 기본 0.05 |
| m₁, m₂ | Phase 3 비대칭 BSGS의 baby step / giant step 크기 | `FindOptimalAsymmetricBSGS` |
| α | PageRank damping factor | 0.85 |
| I | Phase 5 멱법 반복 횟수 | 10 |
| scale | CKKS 인코딩 스케일 | 2⁴⁵ |
| coeff_modulus | CKKS 모듈러스 사슬 | `{60, 45, 45, 60}` |

CKKS 의 `poly_modulus_degree` 는 N 에 따라 자동 결정된다: `2N` 슬롯을 최소로 확보해야 하므로 N = 256 → 8192, N = 2048 → 16384 로 두 배씩 증가한다.

슬롯 패킹은 한 청크가 `2N` 슬롯을 차지하도록 잡혀 있다. 따라서 청크당 유효 슬롯이 N, 남은 N 슬롯은 BSGS 회전 안전을 위한 패딩이다 (3절 참조). 한 SIMD 묶음에 들어가는 평가 대상의 수는 `batch_size = slot_count / pirBlockSize` 로, poly = 8192, N = 1024 이면 slot_count = 4096 → `batch_size = 2`, 즉 한 청크에 두 명까지만 들어간다.

## 1.3 6 단계 흐름

| Phase | 주체 | 입력 | 출력 |
|---|---|---|---|
| 1 | 서버 | BitcoinOTC csv | `M_pub` (1-hop 가중치 행렬), BsgsDiag 리스트 |
| 2 | 클라이언트 | 평가 대상 지갑 ID 목록 | One-hot 벡터의 CKKS 암호문 K 개 |
| 3 | 서버 | 암호문 + BsgsDiag | "이 지갑의 이웃들 weight 분포" 암호문 K 개 |
| 4 | 클라이언트 | 위 암호문 K 개 | 각 대상별 top-K (= nSub) 이웃 인덱스 |
| 5 | 서버 + 클라이언트 | 위 인덱스 + `M_pub` | 부분 그래프 위의 PageRank 결과 |
| 6 | 클라이언트 | PageRank 점수 | `score ≥ 0.0150` 여부로 APPROVED/REJECTED |

Phase 5 가 "서버 + 클라이언트" 인 이유는, CKKS의 useful depth 한계 때문에 매 멱법 반복마다 한 번씩 복호 후 재암호하는 단순화가 들어가 있기 때문이다. 단일-당사자 측정 환경 한정으로 받아들이는 가정이며, 4 절에서 자세히 다룬다.

## 1.4 위협 모델 — 무엇을 숨기는가

서버는 다음을 *모른다*:

1. 클라이언트가 어떤 지갑을 평가 대상으로 골랐는지 (one-hot 인코딩은 CKKS 암호문 안에서만 의미를 가진다).
2. 평가 결과 점수의 실수 값.

서버가 *아는* 것은:

1. 전체 그래프 (BitcoinOTC csv 그 자체는 공개 데이터로 가정).
2. 청크 수 K, BSGS 파라미터 (m₁, m₂), Galois key step 집합. 이들은 N 의 함수이므로 평가 대상에 의존하지 않는다.

이 가정 하에서는 wall-clock 자체가 평가 대상에 무관하다 — 어떤 지갑을 평가하든 BSGS는 같은 수의 회전을 같은 순서로 한다. graph-private 모델(서버에 그래프조차 숨기는 시나리오)로 모델을 확장하면 그때부터는 timing leak 표면이 새로 생기는데, A1·A2·B 설계 문서의 NG 절에서 따로 명시했다.

## 1.5 베이스라인과 두 최적화

baseline (`main` 브랜치) 은 다음 두 군데에서 비싸다:

- **Phase 1**: `M_total = M_pub + M_pub · M_pub` 의 dense 행렬 곱을 N × N × N 으로 돌린다. N=1024 면 ≈ 10⁹ 부동소수점 곱.
- **Phase 3**: 비영 대각선 D 개 각각에 대해 CKKS 회전 1 회. N=1024 면 ≈ 1024 회의 keyswitching.

A1 (`feat/bgsg-experiment`) 은 Phase 3 의 회전 수를 비대칭 Baby-Step Giant-Step 으로 O(m₁ + m₂) = O(√N) 로 줄이고, 청크 루프에 OpenMP 를 얹는다. 부수적으로 Phase 5 에도 같은 BSGS 를 적용하고, Phase 5 의 thread-local SEAL 객체를 정리한다 (H-2 patch).

A2 (`feat/sparse-twohop-precompute-experiment`) 는 Phase 1 의 dense 행렬 곱을 그래프 인접 리스트 기반의 직접 누적으로 바꾼다. 동시에 β₁=1.0, β₂=0.30, θ=0.05 라는 의미 모델 변경을 도입한다. β₂ < 1 은 2-hop 전파를 감쇠하고, θ 는 약한 1-hop 으로부터의 2-hop 전파를 차단한다. 이 변경 때문에 A2 와 baseline 은 결과 점수가 일치하지 않는다 — 같은 지갑에 대해 verdict 가 뒤집히는 사례가 실측에 등장한다 (`Wallet 4`, Config A).

B (`feat/bgsg-sparse-integrated`, 이 브랜치) 는 둘을 결합한다. Phase 1 에서 sparse 알고리즘으로 BsgsDiag 를 만들되 row 범위는 BSGS 가 요구하는 [0, 2N) 까지 채운다 (Q7 패딩). Phase 3 / Phase 5 는 A1 의 BSGS 와 OMP 를 그대로 쓰고, Phase 5 의 dense `M_pub` 접근은 sparse 표현으로 대체한다 (Q5).

## 1.6 출력의 의미

Phase 6 은 평가 대상의 부분 그래프 내 PageRank 점수를 출력한다. 임계값 0.0150 이상이면 `[APPROVED]`, 미만이면 `[REJECTED]` 다. 이 임계값 자체는 코드 안에 하드코딩되어 있고 (`CipherRank.cpp:712`), 의미 모델 (β·θ) 에 따라 같은 지갑이 양쪽으로 갈릴 수 있다.

예를 들어 nGlobal=256, 디폴트 4개 타겟 (`1, 2, 4, 35`) 에 대해 baseline 과 B 의 출력은 다음과 같다.

| Wallet | main score | B-default score | main verdict | B verdict |
|---:|---:|---:|---|---|
| 1 | 0.037138 | 0.041407 | APPROVED | APPROVED |
| 2 | 0.014749 | 0.014749 | REJECTED | REJECTED |
| 4 | 0.014618 | 0.018272 | REJECTED | **APPROVED** |
| 35 | 0.020566 | 0.027752 | APPROVED | APPROVED |

Wallet 4 의 verdict 가 뒤집힌 것은 β₂=0.30 과 θ=0.05 가 약한 1-hop 으로부터의 2-hop 전파를 끊어내는 결과로, 그 결과 자기 그래프 내 PageRank 가 미세하게 올라간 사례다. "같은 시스템 같은 입력에 대해 같은 결과" 가 동형 PIR 의 보장 같지만, *어떤* 동형 PIR 인지에 따라 (= 어떤 의미 모델 위에서 PIR 하는지에 따라) 출력은 분명히 달라질 수 있다는 점을 강조해 둔다.

이후 문서는 각 phase 가 정확히 어떤 계산을 어떤 데이터 위에서 수행하는지를 다룬다.
