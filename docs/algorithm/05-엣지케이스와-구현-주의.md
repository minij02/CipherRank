# 5. 엣지케이스와 구현 주의사항

앞선 네 문서가 정상 경로를 따라간 것이라면, 이 문서는 "이렇게 하면 결과가 미묘하게 어긋난다" 의 카탈로그다. 각 항목은 (1) 어떤 조건에서 일어나는지, (2) 코드가 어떻게 막거나 막지 않는지, (3) 안 막은 경우 후속 작업이 무엇인지를 적었다.

## 5.1 데이터 가정

### 5.1.1 `parts[2] >= 2` 필터의 사각지대

`CipherRank.cpp:354–360` 의 파서가 `parts[2] >= 2` 인 행만 받아들인다. BitcoinOTC 의 weight 분포는 -10 에서 +10 이고, 이 필터는 **음수와 0, 그리고 +1 평점을 모두 버린다**. 정확히 23,611 행이 입력 단계에서 사라진다 (원본 35,592 → 통과 11,981).

이 사실이 의미 모델에 미치는 영향:

- *불신 (distrust) 신호의 완전한 소실*. PageRank 가 보는 그래프는 "신뢰만 흐르는 그래프" 다. 누군가가 sybil 노드에게 -10 의 평점을 줬다고 한들 그 평점이 사라지므로, PageRank 는 "이 노드가 신뢰는 안 받는다" 정도만 알지 "다른 사람들이 명시적으로 의심한다" 는 못 본다.
- *자연 sybil 의 frequency 만 떨어진다*. 자연 sybil 후보 식별이 음수 평점에 의존하는데, 필터 통과 후 그 정보가 사라진다. 그래서 R8'' 의 sybil 후보군은 *원본* csv 의 음수 평점 기록을 *밖에서* 추출해 "이 노드는 평균 incoming 이 음수다" 를 표시로 삼는다.
- *합성 sybil 의 weight 선택*. 합성 dataset 의 sybil-to-sybil 평점을 5 로, 외부 평점을 2 로 잡은 이유가 여기 있다. 외부 평점이 1 이하면 필터에 걸려 사라지므로 sybil 노드의 frequency 가 못 올라가고 top-N 안에 못 들어간다.

이 필터를 완화하면 정보는 늘지만 의미 모델 자체가 바뀐다. "낮은 신뢰" 와 "불신" 을 같은 축에 둘 것인지의 디자인 결정이라, 본 spec 의 범위 밖이다.

### 5.1.2 시간 감쇠로 인한 자동 가지치기

`HALF_LIFE = 1 year` 의 지수 감쇠는 오래된 거래를 자동으로 약화한다. 9 년 전의 weight=2 거래는 `2 × 0.5^9 ≈ 0.004` 로 떨어져 *Phase 1 의 가지치기 임계값 θ = 0.05 보다 한 자리수 작다*. 이런 간선은 outAdj 에는 등록되지만 2-hop 전파에선 항상 잘린다.

데이터셋의 maxTime ≈ 2016 년 1 월이고 csv 의 첫 시점은 2010 년 11 월. 즉 *데이터셋 시점 기준* 5 년이 평균이고, 그 5 년 전 거래의 감쇠 계수는 0.5^5 = 0.03125 다. weight ≥ 32 인 raw 평점이 있어야 시간 감쇠 후에도 1.0 위에 머문다 — BitcoinOTC 의 raw 평점이 ±10 한계라 사실상 모든 5+ 년 거래는 2-hop 전파에서 빠진다.

요약하면 *Phase 1 의 가지치기는 2-hop 의 시간 윈도를 4–5 년 안쪽으로 좁히는 자연스러운 부수 효과* 를 낸다. θ 를 0 으로 두면 (B-C2 모드) 이 윈도가 사라지고 모든 오래된 거래가 약하게라도 2-hop 으로 흐른다.

### 5.1.3 중복 간선의 누적

`outAdj[srcIdx].push_back(...)` 와 `outM_pub[tgtIdx][srcIdx] += w` 는 같은 (src, tgt) 쌍이 여러 줄에 나오면 그 줄들을 모두 누적한다. BitcoinOTC 에서 같은 두 지갑이 여러 번 거래한 사례 (예: 정기적 무역 관계) 는 자연스럽게 가중치가 합쳐진다.

원본 데이터셋에서 한 (src, tgt) 쌍이 평균 1.1 회 등장한다 — 즉 대부분의 쌍은 한 번이지만 일부 쌍은 여러 번이다. 만약 같은 쌍의 여러 거래에 *대립되는 평점* 이 섞여 있으면 (예: 한 번은 +4, 다른 번은 -8), 음수 거래는 필터에 걸려 빠지므로 양수만 누적되어 *왜곡된 합계* 가 만들어진다. 본 spec 은 이를 "필터 가정의 가시적 영향" 으로 분류하고 추가 처리는 하지 않는다.

## 5.2 청크 경계와 회전 안전

### 5.2.1 Q7 패딩이 없을 때 — A2 단독의 잠재 결함

A2 (`feat/sparse-twohop-precompute-experiment`) 만으로는 BsgsDiag 의 row 가 [0, N) 만 채워진다. 그 상태에서 baseline 의 Phase 3 처럼 *d 개 대각선 각각을 d-슬롯 회전* 하면 청크 영역 [c · 2N, c · 2N + N) 안에서만 회전이 일어나므로 안전하다.

문제는 BSGS 의 giant step 회전이 *2N 영역* 안의 슬롯을 움직이지 [0, N) 만 보지 않는다는 점이다. 회전 결과가 청크 영역의 뒤 N 슬롯 (즉 [c · 2N + N, c · 2N + 2N)) 으로 떨어질 수 있는데, A2 단독에선 그 영역이 *0 으로 채워져 있다*. 그 영역에 의도된 값이 없으니 곱셈 결과가 의도된 값에서 빠진다.

증명은 통합 spec sec 3.1 의 C8 보조정리에 분해되어 있다. 핵심은: 청크 c 의 슬롯 분포가 청크 c' 의 슬롯 분포와 *같은 함수* 라면, 회전이 청크 영역 안에서 어떻게 분포해도 *의도된 값* 이 슬롯에 정확히 있다는 점이다. 이 "모든 청크가 같은 패턴" 가정이 깨지지 않으려면 row ∈ [0, N) 의 값을 row ∈ [N, 2N) 에도 같은 값으로 *복제* 해야 한다 — 이게 Q7 패딩이다.

### 5.2.2 Q7 패딩의 코드

통합 브랜치는 `CipherRank.cpp:489–492` 에서

```cpp
int slot_idx = (row + j * m1) % nGlobal;
diag[c * pirBlockSize + slot_idx] = val;
diag[c * pirBlockSize + slot_idx + nGlobal] = val;     // Q7
```

로 같은 값을 두 군데에 적는다. 이 두 줄 중 한 줄이라도 빠지면 R6'' (multi-chunk equivalence) 가 즉시 실패한다. R6'' 는 5 청크 환경에서 실측되며 (Config B), 어느 청크에서도 점수가 drift 하지 않는지가 검증 가능한 형태로 검출된다.

### 5.2.3 청크 영역과 slot_count 의 정합성

`slot_count` 가 `pirBlockSize = 2N` 의 정수배가 아니면 마지막 청크 끝에 *틈* 이 생긴다. 이 틈은 0 으로 채워져 있지만, 회전이 slot_count 단위 cyclic 이라 첫 청크의 첫 슬롯과 마지막 청크의 끝 슬롯이 *서로 wrap-around* 한다.

코드 (`CipherRank.cpp:447`):

```cpp
batch_size = min(pirCapacity, prCapacity);
num_chunks = ceil(static_cast<double>(num_targets) / batch_size);
```

으로 `num_chunks · pirBlockSize ≤ slot_count` 를 보장하지만, 등호는 일반적으로 성립하지 않는다. 다행히 첫 청크 첫 슬롯의 회전 후 도착지가 마지막 청크 끝 *그 슬롯* 인 경우는, 마지막 청크 끝이 0 인 한 무해하다 — 0 + 무엇은 결과에 영향을 주지 않는다.

이 "마지막 청크 너머는 0" 조건이 깨지는 시나리오를 spec sec 3.1 의 C7 으로 따로 분리해 두었다. 현 코드에선 그 시나리오가 발생할 수 없으나, 누가 빈 슬롯을 다른 용도로 쓰면 (예: 측정 정보 인코딩) 즉시 깨진다.

## 5.3 Galois key step set

CKKS 의 회전은 *어떤 step* 을 회전할지 마다 별개의 Galois key 가 필요하다. SEAL 의 `create_galois_keys()` 기본은 2^k step 만 생성하고, 임의 step 회전은 그 2^k step 들을 합성해서 수행한다. 합성이 가능한 대신 *느리다* — 하나의 임의 step 회전이 여러 번의 key-switching 으로 분해된다.

본 코드는 BSGS 의 baby step (1..m₁-1) 과 giant step (m₁, 2m₁, ...) 을 명시적으로 step set 으로 줘서 (`CipherRank.cpp:296`) Galois key 를 그 step 들에 맞게 *직접* 생성한다. 그렇게 하면 임의 step 회전이 한 번의 key-switching 으로 끝난다.

```cpp
if (galois_step_set_.empty()) {
    for (int i = 1; i <= nGlobal; i++) galois_step_set_.push_back(i);
}
keygen.create_galois_keys(galois_step_set_, galois_keys);
```

`galois_step_set_` 은 `RunPipeline` 안에서 BSGS 결정 직후 채워진다 (`CipherRank.cpp:213–229`):

```cpp
BSGSParams pirParams = FindOptimalAsymmetricBSGS(nGlobal, 1.0);
BSGSParams prParams  = FindOptimalAsymmetricBSGS(nSub,    1.0);
vector<int> stepsPir = ComputeBSGSStepSet(pirParams, nGlobal);
vector<int> stepsPr  = ComputeBSGSStepSet(prParams,  nSub);
set<int> unionSet(stepsPir.begin(), stepsPir.end());
unionSet.insert(stepsPr.begin(), stepsPr.end());
unionSet.insert(1); unionSet.insert(16);    // 측정 dummy 회전용
galois_step_set_.assign(unionSet.begin(), unionSet.end());
```

여기서 *중요한 함정* 이 두 가지 있다.

1. **`unionSet` 에 1 과 16 의 명시적 삽입**: Phase 5 의 weight 측정 dummy 회전 (`CipherRank.cpp:751, 757`) 이 step 1 과 step 16 을 쓴다. 측정에 사용되는 step 까지 step set 에 넣지 않으면 SEAL 가 throw 한다. 이 의존성을 발견할 자리가 코드 안에 따로 없으므로 (테스트 회전이 실패하면 비로소 알게 됨) 주석으로 명시해 두는 게 안전.
2. **weight=1.0 가정의 함의**: weight 측정 결과가 1.0 이 아니라 (예: 2.0) 이라면 `FindOptimalAsymmetricBSGS` 가 다른 (m₁, m₂) 를 반환해야 한다. 그러면 Galois key step set 도 다시 계산해야 하고, 키도 다시 생성해야 한다. 이 *두 번째 생성* 단계 (spec 의 B0 풀 Three-Pass) 가 현재는 구현되지 않았다. weight=1.0 의 cap [1.0, 5.0] 으로 잡힌 코드를 보면 (`CipherRank.cpp:769`) 실측 weight 가 그 범위 안에 들어가도 (m₁, m₂) 의 결정에 영향을 주지 못한다.

후속 작업으로 남겨두었고, 이 머신에서 실측한 baby/giant 비율이 거의 1.0 이라 실용적 회귀는 발생하지 않았다.

## 5.4 β₂ = 0 의 transparent ciphertext

가장 구체적인 버그 사례다. 2 절 2.6 에서 잠깐 언급했지만, 핵심을 다시 풀자.

β₂ = 0 으로 두면 2-hop 누적의 모든 contribution 이 0 이다. 그 결과 `sparseDiag[d][row]` 가 1-hop 만의 contribution (β₁ · w₁) 을 받는데, *일부 d 에 대해서는 1-hop 도 비어있다*. 코드는 sparseDiag 의 entry 자체로는 비어있지 않은 d 만 인코딩하지만, β₂ = 0 인 경우에는 entry 가 *비어있지 않으나 값이 모두 0* 인 d 가 존재한다.

그런 d 가 인코딩되면 BsgsDiag 의 plaintext 가 *전부 0* 인 평문이 된다. BSGS Phase 3 의 다음 단계 (`multiply_plain_inplace(baby_step, plainDiag)`) 가 그 평문을 곱하면 결과 ciphertext 의 모든 슬롯이 0 인 *transparent ciphertext* 가 만들어진다. SEAL 는 이런 ciphertext 가 보안상 위험하다는 이유로 명시적 예외를 던진다 (`std::logic_error: result ciphertext is transparent`).

수정은 단순하다 (`CipherRank.cpp:475–478`):

```cpp
for (int d = 0; d < nGlobal; d++) {
    for (const auto& [row, val] : merged[d])
        if (val != 0.0) sparseDiag[d].emplace_back(row, val);
}
```

reduce 결과를 sorted vector 로 옮길 때 `val != 0.0` 인 항목만 남긴다. 그러면 β₂ = 0 의 d 가 entry 가 모두 0 이면 sparseDiag[d] 가 비게 되고, 그 다음의 인코딩 루프가 `sparseDiag[d].empty()` 가드로 그 d 를 건너뛴다.

이 버그가 발견된 경위가 학술적으로 흥미롭다. fine β·θ grid sweep 의 첫 시도가 β₂ ∈ {0.0, 0.3, 1.0} 의 9 cell 중 β₂ = 0 행 전체에서 SEAL 예외로 죽었다. 가지치기·BSGS·Phase 5 같은 핵심 알고리즘 변경이 아니라, *암호학 라이브러리의 zero-padding 가정* 이 변경의 갈라진 틈을 노출시킨 경우다. 비슷한 유형의 버그가 후속 변경 (Q3, B8 의 main-style fallback) 에서도 발생할 가능성이 있다.

## 5.5 CKKS scale 관리

BSGS 의 누적은 `multiply_plain` → `rescale_to_next_inplace` → `add_inplace` 의 순서로 이뤄진다. CKKS 의 `multiply_plain` 은 두 인자의 scale 을 곱하고, rescale 은 그 곱한 scale 을 한 단계 prime 으로 나눠 *원래 scale 에 근접한* 값으로 되돌린다. 정확히 같지는 않다 — prime 의 실제 값이 scale 의 정수배가 아니라 미세한 비율로 어긋난다.

이 비율 차이가 누적되면 ciphertext 들 사이의 scale 이 미세하게 흩어지고, `add_inplace` 가 *scale mismatch* 로 던진다. 이를 막기 위해 코드는 매 rescale 후

```cpp
multiplied.scale() = scale;
```

로 scale 을 *강제 동일* 로 맞춘다. 수학적으로 보면 ciphertext 안의 값이 약간 비율적으로 어긋난 상태로 더해지는 것이지만, 실측 결과 차이는 노이즈 floor 안에 묻힌다. R1'' 의 ε ≈ 0 결과가 그 증거다.

`mod_switch_to_inplace` 도 같은 맥락이다. 누적 결과의 modulus chain 레벨을 새 ciphertext 의 레벨로 *맞춰* 더할 수 있게 한다. modulus chain 이 같지 않으면 SEAL 가 add 를 거부한다.

## 5.6 unordered_map 의 cross-run 결정성

libstdc++ 와 libc++ 의 `unordered_map` 은 *해시 함수의 시드* 가 process 안에서는 결정적이지만 *프로세스 간 동일성을 보장하지는 않는다*. 같은 입력에 대해 다른 프로세스 (예: 다른 시점의 binary 실행) 에서 iteration order 가 다를 수 있다.

이 비결정성이 영향을 주는 곳:

- `frequency` 의 빈도 동률 노드들의 인덱스 순서. 두 노드가 같은 frequency 이면 어느 쪽이 더 작은 인덱스를 받을지 unordered_map 의 iteration 에 의존한다. BitcoinOTC 의 상위 1024 명은 대부분 frequency 가 다 다르므로 실측에선 영향 없다.
- `sparseDiag` 자체. 하지만 Q4 baseline 으로 `std::map` 를 거쳐 sorted vector 로 직렬화하므로 *직렬화 후* 의 순서는 결정적이다.

후자가 해결되어 있다는 점이 중요하다. *직렬화 시점* 의 결정성은 std::map 의 sorted 순회로 강제되고, *부동소수점 누적 순서* 는 thread_id 순서로 강제되며, *읽기 순회* 는 plaintext encode 가 한 번에 일어나기 때문에 더 이상 cross-run 비결정성이 점수에 영향을 주지 않는다.

## 5.7 단일-당사자 모델의 한계

본 코드의 Phase 5 가 매 iter 복호 + 재암호 를 하므로, 서버는 *secret_key 를 가지고 있다*. 이건 진짜 PIR 위협 모델이 아니다 — PIR 의 의미는 "서버가 클라이언트의 질의 내용을 모른다" 이고, secret_key 를 갖고 있으면 모든 ciphertext 의 평문을 본다.

본 시스템에서 *유일하게* 의미가 있는 보안 보장은 다음이다.

- *Phase 3 의 출력은 평가 대상 인덱스의 명시적 함수가 아니다* (one-hot 의 위치는 ciphertext 안에서만 의미를 가진다).
- *wall-clock 은 평가 대상에 무관하다* (BSGS 가 같은 수의 회전을 같은 step set 으로 한다).
- *연산 데이터 (BsgsDiag, M_pub) 는 평가 대상에 무관하다* (Phase 1 에서 한 번 만들고 끝).

진짜 PIR 시나리오로 가려면 (1) Phase 5 의 decrypt + re-encrypt 를 동형 normalization 으로 교체하거나, (2) Phase 5 의 iter 수를 1–2 로 줄여 useful depth 안에 가두거나, (3) bootstrapping 을 도입해야 한다. 셋 다 별개 spec 의 후속 작업이다. 본 측정값은 *알고리즘 수준의 wall-clock 비교* 로만 받아들여야 한다.

## 5.8 측정의 함정

### 5.8.1 열 부하

장시간 sweep 을 돌리면 wall-clock 이 25–40% 정도 늘어나는 현상이 반복적으로 관찰됐다. 측정 사이에 60 초 idle 을 두면 회복된다. 한 cold 한 batch (1 회) 의 measurement 가 가장 정확하지만 통계적 강도가 낮고, warm batch (N 회 연속) 가 통계적 강도는 높지만 *시스템 부하* 가 측정에 섞인다.

본 sweep 결과는 다음 원칙으로 보고했다.

- **단일 측정** (Phase-γ 첫 단계, MVB) 은 cold 머신 기준.
- **N=3 sweep** 은 측정 사이의 짧은 휴식만 두고 진행 — warm 머신 영향이 일부 섞임.
- **N=10 batch** 는 sustained-load 환경. R10'' 의 8.5 s outlier 가 여기서 나왔다 — 의도된 측정이고 thermal artifact 임을 분명히 명시했다.
- **합성 sweep 의 일부 cell (β₂=1.0, θ ≤ 0.05)** 은 한 run 이 1056 초까지 갔다. 동일 cell 의 cold 측정은 3.7 초. 75× 의 변동이 시스템 부하만으로 설명되는 사례.

이 변동을 *논문급으로 깔끔하게* 정리하려면 별도 측정 환경 (사실은 별도 머신, 또는 reserved EC2 인스턴스) 이 필요하다. 본 spec 은 단일 머신 한계 안에서 honest reporting 을 우선했다.

### 5.8.2 OMP 스레드 수의 상한

OpenMP P = 4 가 사실상의 최적이다. P = 8 까지는 5 청크 (Config B) 가 두 batch 로 끝나서 가속이 의미 있지만, P = 16 은 oversubscription 이라 thread 간 cache contention 으로 *느려진다*. 이건 머신의 코어 수 (4) 와 청크 수 (5) 의 곱셈적 한계라 코드 변경으로 못 푼다 — 청크 수가 더 늘어나는 시나리오 (예: num_targets = 256) 에서만 P > 4 가 의미를 갖는다.

### 5.8.3 verdict 가 같다고 알고리즘이 같은 건 아님

Phase 6 의 `[APPROVED] / [REJECTED]` 출력은 임계값 0.0150 위·아래만 본다. 그 위·아래의 *실제 점수* 가 다르면 알고리즘이 다른 것이다. baseline 과 B-default 가 같은 verdict 를 내는 경우라도 점수는 보통 다르다 (1절 1.6 의 Wallet 1, 35 예시). R8'' 의 TPR/FPR 만 보면 "모드들이 같다" 처럼 보이는 위험이 있어, R1''/R2''/R6'' 는 *점수의 ε-equivalence* 까지 본다.

## 5.9 후속 항목

본 spec 의 deferred 항목들은 README 와 followup-results sec 5 에 표로 정리했지만, 알고리즘 관점에서 다시 짚으면:

- **B0 풀 Three-Pass**: weight 자동 측정 → BSGS 파라미터 결정 → Galois key 재생성 의 사이클. 현재는 weight=1.0 고정으로 우회되어 있다.
- **B2 phase_kind cost function**: Phase 3 와 Phase 5 의 BSGS 비용이 *다른 차원* 의 행렬이라 따로 최적화해야 한다. 현재는 같은 cost 함수에 N, n 만 다르게 넣어 호출하는 약식.
- **B8 main-style fallback**: D_sparse 가 작으면 BSGS 가 baseline 보다 *느릴* 수 있다 — 이때 baseline 의 직접 회전 경로로 분기. 현재는 advisory log 만.
- **Q3 hub-aware Phase 1**: hub 노드의 2-hop 누적이 평균보다 압도적으로 큰 경우, 그 노드만 따로 처리하면 sweep 시간이 더 단축될 수 있다. 단 sybil 시나리오 변경 가능성이 있어 별도 보안 분석이 필요.
- **Hub-trust-mixed 합성 sybil**: 현재 합성 sybil 은 *완전히 격리된* mutual ring 이다. 만약 sybil 이 실제 trust 허브와도 약하게 연결되어 있다면 (i.e. 위장된 sybil), B-default 와 B-C2 의 차이가 그제서야 의미 있게 나올 수 있다. 후속 사용자 케이스 검증이 필요.
- **Multi-dataset 일반화**: BitcoinOTC 의 weight 스케일과 시간 분포 가정이 다른 데이터셋으로 옮길 때 어떻게 무너지는지. β, θ 의 의미가 데이터셋마다 다시 calibrate 되어야 한다는 점이 spec 의 NG11 (데이터셋 일반화 부재).

각각 spec 안의 NG / O 절에 cross-reference 되어 있다.

## 5.10 β₂ = 0 의 transparent ciphertext — 손 트레이스

5.4 의 설명만으론 어떤 d 가 transparent 가 되는지 잘 안 보인다. 2 절 2.9 의 N=4 예제로 *정확히 어디서* 0 평문이 만들어지는지 따라간다.

같은 6 줄 csv 에 β₂ = 0 을 주면 2-hop 누적의 모든 항이 0 으로 떨어진다. 1-hop 만 남기고 sparseDiag 를 다시 계산하면

| d | 1-hop 누적 결과 (β₂ = 0 의 경우) |
|---:|---|
| 0 | 비어있음 (self-loop 없음) |
| 1 | { 0 : 4, 1 : 5 } |
| 2 | { 2 : 4, 3 : 2 } |
| 3 | { 0 : 3, 1 : 3 } |

해석: d = 1 의 (src − mid) mod 4 = 1 인 1-hop 간선만 본다. src = 1, mid = 0 (= 30 → 10, w = 4) 가 `(d=1, row=0)` 에 4 를 넣고, src = 2, mid = 1 (= 20 → 30, w = 5) 가 `(d=1, row=1)` 에 5 를 넣는다. d = 2, d = 3 도 같은 방식. d = 0 은 self-loop 가 있어야 채워지는데 BitcoinOTC 에는 self-loop 가 없으니 *비어있다*.

검산: M_pub 의 d-번째 대각선과 비교.

- d = 0: (0, 0, 0, 0) — 모두 0, 비어있음 ✓
- d = 1: (M[0][1], M[1][2], M[2][3], M[3][0]) = (4, 5, 0, 0). 0 이 아닌 것만 남기면 {0:4, 1:5} ✓
- d = 2: (0, 0, 4, 2) → {2:4, 3:2} ✓
- d = 3: (3, 3, 0, 0) → {0:3, 1:3} ✓

전부 일치.

### 5.10.1 가드 없으면 어디서 터지는가

`if (val != 0.0)` 가드가 없는 코드가 위 β₂ = 0 입력을 받으면 어떻게 되는가? Phase 1 의 누적 루프가 *2-hop 시도* 자체는 한다는 게 핵심이다. β₂ = 0 이라 결과값이 0 일 뿐, `localDiag[d2][dst] += β₂ · w₁ · w₂` 라인은 매 (src, mid, dst) 트리플에서 한 번씩 실행된다. `unordered_map<int, double>` 의 `operator[]` 가 키가 없으면 0 으로 자동 삽입하므로, *값은 0 이지만 entry 는 존재* 하는 `(dst, 0.0)` 항목이 누적된다.

이 entry 들이 reduce 단계까지 살아남는다. `merged[d][dst] += 0.0` 가 일어나면 std::map 에 `(dst, 0.0)` 가 정식 entry 로 남는다. 가드 없이 sorted vector 로 옮기면 sparseDiag[d] 가 *값이 모두 0 인 entry 만 가진* 비어있지 않은 vector 가 된다.

코드의 `if (sparseDiag[d].empty()) continue;` 가드는 *비어있는* d 만 건너뛴다. *값이 모두 0 인데 entry 가 존재* 하는 d 는 통과한다. 그 d 가 BsgsDiag 인코딩 단계로 들어가서, 모든 슬롯이 0 인 vector → encode → 모든 계수가 0 인 Plaintext 가 만들어진다.

본 예제에 대입해 보자. β₂ = 0 + 가드 없음 으로 돌리면, src = 0, mid = 2 의 2-hop 시도 `localDiag[3][1] += 0` 가 `(d=3, row=1, val=0.0)` entry 를 만든다 (1-hop 으로도 d = 3, row = 1 에 3 이 들어오므로 합쳐서 3.0 으로 살아남지만, 다른 자리에선 2-hop 만의 0 entry 가 남는다). 더 분명한 예로 `localDiag[0][0] += 0` (src=0, mid=1, dst=0 의 2-hop) 는 d=0 에 row=0 의 0 entry 를 만든다. d = 0 은 1-hop 으로는 비어있던 자리라, 가드 없으면 `sparseDiag[0] = [(0, 0.0)]` 로 *값은 0 인데 비어있지 않은* 상태가 된다.

### 5.10.2 SEAL 가 던지는 자리

Phase 3 의 다음 줄

```cpp
thread_evaluator.multiply_plain_inplace(multiplied, item.plain);
```

이 `item.plain` 이 모두 0 인 경우, 결과 ciphertext 의 모든 슬롯이 0 으로 떨어진다. SEAL 의 정의상 이런 ciphertext 는 *transparent* — 비밀키 없이도 평문이 모두 0 임이 자명. 보안 위험으로 분류되어

```
terminate called after throwing an instance of 'std::logic_error'
  what():  result ciphertext is transparent
```

이 exception 의 정확한 발생 자리가 위의 multiply_plain_inplace 호출. 본 예제의 d = 0 평문 곱 (= 첫 번째 (i = 0, j = 0) 의 BsgsDiag 와 baby_steps[0] 의 곱) 에서 즉시 터진다.

### 5.10.3 수정 한 줄과 sweep 정상화

`CipherRank.cpp:464–468`

```cpp
for (int d = 0; d < nGlobal; d++) {
    for (const auto& [row, val] : merged[d])
        if (val != 0.0) sparseDiag[d].emplace_back(row, val);
}
```

`val != 0.0` 가드가 reduce 후 sorted vector 로 옮길 때 *값이 0 인 entry 를 통째로 버린다*. β₂ = 0 의 모든 d 에 대해 2-hop 기여만 있던 entry 가 모두 사라지고, 1-hop entry 만 남은 d 또는 *완전히 비어있는* d 가 된다. 완전히 비어있는 d 는 `sparseDiag[d].empty()` 가드에 걸려 BsgsDiag 인코딩을 건너뛴다.

본 예제 (β₂ = 0) 에서는 가드 한 줄 추가 후 d = 0 이 비어있어 인코딩 스킵, D_sparse = 3 으로 떨어진다. d = 1, 2, 3 은 정상 인코딩, multiply_plain 결과도 transparent 가 아니다. exception 없이 Phase 3 끝까지 통과한다.

발견 경위가 학술적으로 흥미롭다. fine β·θ grid sweep 의 첫 시도 (β₂ ∈ {0.0, 0.3, 1.0}) 의 β₂ = 0 행 *9 cell 전부* 가 위 exception 으로 죽었다. β·θ 의 *의미* 모델 변경의 부수 효과가 *암호학 라이브러리의 zero-padding 가정* 을 노출시킨 사례 — 알고리즘 수준의 변경이 의도치 않은 자리에 함정을 만든다는 점에서 비슷한 패턴의 후속 버그를 예측하는 단서가 된다 (Q3, B8 의 main-style fallback 도입 시 비슷한 손 트레이스를 미리 해두는 게 안전).
