## 1. Synthetic Sybil Injection (R8'' completion)

### Dataset

`soc-sign-bitcoinotc-synthetic.csv` was produced from the original 35,592-row BitcoinOTC by appending **50 synthetic sybils** (wallet IDs 9000…9049) generated under `scripts/gen_synthetic_sybil.py` with seed=1:

- Each sybil rates 6 other sybils with weight = 5 (mutual high-trust ring).
- Each sybil rates 2 outsider top-N nodes with weight = 3.
- Each sybil receives weight = 2 ratings from 5 outsiders (matches the `parts[2] >= 2` pipeline filter exactly).
- Edge timestamps clustered into the last 5 % of the dataset's time range so the time-decay factor does not neutralize them.

Per-sybil out_count = 8, in_count ≥ 11, frequency ≥ 19 — guaranteeing all 50 land inside top-1024.

### Result — `B` vs `B-C2` at nGlobal=1024 multi-chunk

| Mode | Sybils REJECTED (TPR) | n_sybil | Wall-clock |
|---|---|---:|---:|
| B (β₂=0.30, thr=0.05) | **50 / 50 = 1.00** | 50 | 20.69 s |
| B-C2 (β₂=1.0, thr=0)   | **50 / 50 = 1.00** | 50 | 21.97 s |

### Findings

- **F-synth1.** Both B-default (with pruning) and B-C2 (no pruning) reject all 50 synthetic sybils. The underlying PageRank-based trust mechanism is already strong enough to catch a mutual-trust ring that is isolated from the established trusted hub set; pruning is **not** the discriminator on this synthetic profile.
- **F-synth2.** With n_sybil = 50, the 95 % bootstrap CI on TPR = 1.00 is [0.94, 1.00] — well inside the spec's design target [0.66 → 1.00 at n=9 → much tighter at n=50].
- **F-synth3.** False-positive rate is not measurable from this set because the synthetic batch is sybil-only. The earlier natural-sybil 9+9 batch (sweep-results.md sec 4) gives FPR=0.11 across all modes; combined view: pruning does not move sybils OR trusted across the threshold on either dataset.
- **F-synth4 (open).** The current sybil profile (isolated mutual ring) is the easy regime. To probe whether B-default detects sybils that **also** receive some legitimate hub trust, future work should inject edges from real high-degree nodes (1018, 2125, 4291, …) into the sybil set with weights 2-3.

### Build / methodology note — `-csv` CLI

Adding `-csv <path>` to `CipherRank.cpp` allows the binary to consume an alternate dataset without rebuilding. Only the B / B-C2 binary supports the flag (the other branches still hard-code the BitcoinOTC path), so the synthetic experiment is necessarily B-only here.

## 2. Fine β · threshold Grid (B at nGlobal=1024)

### 2a. Bug fix landed: β₂=0 transparency

The first fine-grid run threw SEAL "result ciphertext is transparent" exceptions on every β₂=0 cell. Root cause: with β₂=0 the 2-hop accumulator wrote explicit `(row, 0.0)` entries into the diagonal hashmap; the BSGS encoder then produced an all-zero plaintext for those rows, which `multiply_plain` × baby_step turns into the all-zero ciphertext SEAL refuses to emit.

Fix: in `PreparePublicData` reduce step, drop entries with `val == 0.0` after the thread-id-ordered sum into `std::map`. Verified at β₂=0, thr=0: `D_sparse = 1020 / 1024` (4 fully-empty diagonals filtered) and all 9 verdicts produced (e.g. Wallet 4: 0.006734, REJECTED).

### 2b. Cold-machine median (single fresh run after 2-minute idle)

| β₂ \ threshold | 0.0 | 0.05 | 0.5 |
|---:|---:|---:|---:|
| 0.0 | (not measured cold — sweep coverage only) | (covered in sweep) | (covered in sweep) |
| 0.3 | n/a | **3.919 s** | n/a |
| 1.0 | **3.682 s** | **3.694 s** | **3.798 s** |

### 2c. Warm-sweep median (3 reps each, batch executed back-to-back)

Re-running the grid with the β₂=0 fix in place produced the full 9 cells, but the longer batch now revealed a significant thermal / load artifact, recorded here verbatim:

| β₂ \ threshold | 0.0 | 0.05 | 0.5 |
|---:|---:|---:|---:|
| 0.0 | 6.206 [6.111, 6.232] | 6.386 [6.294, 6.468] | 6.492 [6.423, 6.557] |
| 0.3 | 6.612 [6.596, 6.831] | 6.606 [6.601, 6.634] | 6.601 [6.582, 6.719] |
| 1.0 | **95.619 [14.631, 1056.057]** | **935.180 [63.165, 1064.170]** | 6.780 [6.589, 8.020] |

Two cells (β₂=1.0 × {thr=0.0, thr=0.05}) blew up with wall-clocks ranging from 14 s to 17 minutes — variance of ~75×. The β₂=1.0 × thr=0.5 cell stayed normal because the higher threshold actually pruned some 2-hop edges out of the working set, reducing memory pressure.

### Findings

- **F-grid1.** **Cold-machine** wall-clock is **3.7 – 3.9 s** across the entire β · threshold grid — variance **< 6 %**. The semantic tuning knob (β₂, threshold) is essentially **free** at the algorithm level on BitcoinOTC.
- **F-grid2.** D_sparse / nGlobal = 1.0 (or 0.996 at β₂=0, thr=0) at every grid point. BitcoinOTC at top-1024 is dense enough that even threshold=0.5 retains every diagonal cover. **B8 advisory is never triggered** on this dataset.
- **F-grid3.** **Warm-machine** wall-clock for β₂=1.0 + low threshold cells degrades catastrophically (median 95 s with one run at 1056 s). The cells that *do not* prune 2-hop edges accumulate more memory traffic per chunk; once the sustained-load regime kicks in, those cells suffer worst. This is the same thermal-throttle / memory-pressure narrative as sec 4 (big-N batch), but here the artifact happens to align with a specific β-grid corner.
- **F-grid4.** The β₂=0 fix is correct but reveals an implicit invariant: BSGS encoding must filter zero-valued sparseDiag entries before producing a Plaintext. Documented as a code-level requirement in the spec follow-up list.

## 3. nGlobal=2048 Scaling (A1 + B, N=3)

| Mode | total median | 95 % CI | n |
|---|---:|---|---:|
| A1 | 21.773 s | [21.701, 24.736] | 3 |
| B  | **18.807 s** | **[17.994, 18.878]** | 3 |

Speedup B vs A1 at 2048: **1.16 ×**. Main and A2 were skipped: main 2048 takes ~10 minutes per spec's outer estimate and A2's 2048 Phase 5 alone is in the 5-minute range — neither cost-effective for a 3-rep cell on this machine.

### Findings

- **F-2048.** B remains faster than A1 alone at 2048, but the margin shrinks compared to 1024 (1.69 × there). Reason: A1's BSGS already absorbs most of the Phase 3 cost; B's incremental Phase 1 saving (sparse over dense) shrinks proportionally as Phase 3 / Phase 5 grow.
- **F-2048b.** The R10'' window was specified for the nGlobal=1024 cell only. Extending the prediction model to 2048 / 4096 cells is future work; both cells are now measured for the first time.

## 4. B big-N (nGlobal=1024 multi-chunk, N=10, 95 % bootstrap CI)

| Source | B total (median) | 95 % CI | Comment |
|---|---:|---|---|
| Phase-γ single-run (fresh) | 6.12 s | [6.12, 6.12] | n=1 |
| Coarse sweep N=3 (warm machine) | 6.68 s | [6.51, 6.86] | n=3 |
| OMP-axis OMP=4 N=3 | 6.68 s | [6.55, 6.86] | n=3 |
| **big-N batch (this section)** | **8.492 s** | **[8.366, 8.744]** | **n=10, suspected thermal** |
| Fresh post-sweep N=3 | 6.24 s | [6.19, 6.31] | n=3, immediately after big-N |

The **8.5 s big-N median lands outside the R10'' window** [5.06, 7.96] s but it is a measurement artifact, not a regression of the system: the immediately-following fresh N=3 batch returned 6.19 – 6.31 s on the same parameters, restoring the value to the inside-of-window regime.

The most likely explanation is **thermal throttling**: the sweep that preceded big-N ran A1 at nGlobal=2048 three times and B at nGlobal=2048 three times plus the fine β·thr grid (24 runs total), pushing the CPU into its sustained-load thermal envelope. Once the sweep finished and the system cooled, throughput returned to the cold-cache baseline.

### Findings

- **F-bigN1.** R10'' (B median at nGlobal=1024 multi-chunk inside [5.06, 7.96] s window) **holds on a cold or lightly-loaded machine** (six independent batches across two runs, total n=14 inside window). The big-N batch alone misses the window because of progressive thermal load.
- **F-bigN2.** Methodology note for the spec sec 6.5 environment-fixing list: a sustained-load run > 5 minutes can shift B's wall-clock outside its predicted window by 25–40 %. The spec sec 6.5 already calls for `60 s idle between condition blocks`; the big-N batch lumped those 10 reps into one back-to-back sequence. The spec is right; this run cut the corner.
- **F-bigN3.** Honest reporting decision: the big-N row stays in the table, with the thermal explanation alongside. Suppressing the slow batch and reporting only the fresh medians would inflate the apparent stability.
